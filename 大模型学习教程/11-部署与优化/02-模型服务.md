# 模型服务

## 服务系统多做了什么

单次离线推理只需处理一个输入；在线模型服务（Model Serving）还要同时管理请求到达、排队、批处理、KV Cache、采样、流式输出、取消、超时、限流和故障。系统目标通常包含：

- 首 token 延迟（Time to First Token，TTFT）；
- 每个输出 token 延迟（Time per Output Token，TPOT）；
- 吞吐（Throughput）；
- 尾延迟（如 P95/P99 Latency）；
- 单位请求成本与稳定性。

这些目标会冲突。更大的批次通常提高吞吐，却可能增加排队时间。

先读：[[../15-概念词典/22-连续批处理与分页KV缓存|连续批处理与分页 KV 缓存]]。

## 1. Prefill 与 Decode

一次生成分两段：

### Prefill（提示处理）

模型并行处理提示中的多个 token，建立首批 KV Cache。长提示会增加计算量，并提高 TTFT。

### Decode（逐 token 解码）

每轮为每个请求生成一个新 token，并读取已有 KV Cache。单轮矩阵较小，但要反复执行，常更受显存带宽和调度开销影响。

服务系统若把很长的 prefill 与短 decode 混在同一队列，可能让正在生成的请求卡顿。不同引擎会采用分块 prefill、优先级或分离调度，行为随版本变化 `[C]`。

## 2. 静态批处理为什么浪费

假设同一批中：

- 请求 A 生成 2 个 token；
- 请求 B 生成 20 个 token。

若静态批次必须等 B 结束，A 完成后的槽位会空闲 18 轮。新请求 C 即使已经到达，也要等待下一批。

## 3. 连续批处理

连续批处理（Continuous Batching，也称 Inflight Batching）在每个解码步更新活动集合：

```text
第1轮: A B
第2轮: A B  → A结束
第3轮: C B
第4轮: C B D
```

调度器每轮要检查：

1. 哪些请求已完成或取消；
2. 哪些 KV 块可以释放；
3. 队列中的哪些请求能放入剩余容量；
4. 每个请求的采样状态和停止条件；
5. 是否触发超时或抢占。

它提高的是整体利用率，不保证每个请求延迟都降低。如果队列追求最大吞吐，低优先级请求可能等待更久。

## 4. PagedAttention

PagedAttention 将每个序列的 KV Cache 切成固定大小块，并用块表把逻辑块映射到不连续的物理显存块 `[A]`：

```text
逻辑块: 0  1  2
物理块: 7  3  9
```

请求增长时按需分配，结束时归还。块大小 16 token、当前长度 33 token 时，需要：

$$
\left\lceil\frac{33}{16}\right\rceil=3
$$

个块。最后一块只使用 1 个槽位，因此分页减少但不能消除内部碎片。

### 前缀共享

多个候选共享同一提示时，可让块表引用相同的只读前缀块；序列分叉后再为新增 token 分配不同块。共享是否可用取决于引擎、采样流程和缓存策略。

## 5. 容量估算

KV Cache 大小随层数、Key/Value 头数、头维度、序列长度、批量和数据类型增长。完整计算见 [[../16-公式手册/17-KV-Cache容量公式|KV Cache 容量公式]]。

服务容量不能只用模型权重显存估算。还要预留：

- KV Cache；
- 临时激活和算子工作区；
- 通信缓冲；
- CUDA 图或其他运行时缓存；
- 显存碎片和安全余量。

## 6. vLLM 与 TensorRT-LLM

### vLLM

vLLM 是开源 LLM 推理与服务引擎，提供 PagedAttention、连续批处理和 OpenAI 兼容 API。支持模型、量化格式和参数会随版本变化，部署时应固定版本并运行目标硬件实测 `[A/C]`。

### TensorRT-LLM

TensorRT-LLM 是 NVIDIA 面向 NVIDIA GPU 的开源推理库，包含图优化、定制内核、量化、多 GPU 并行与 inflight batching。它不是跨所有硬件的通用性能结论 `[A]`。

## 7. 吞吐与延迟怎样权衡

| 调整 | 可能收益 | 可能代价 |
|---|---|---|
| 增大批次 token 数 | GPU 利用率和吞吐提高 | 排队、TTFT 或显存上升 |
| 增大 KV Cache 预留 | 可容纳更多并发/上下文 | 留给权重和工作区的显存减少 |
| 量化权重 | 权重内存和带宽下降 | 精度变化；无匹配内核时未必更快 |
| 缩短最大上下文 | 容量更可控 | 无法服务长请求 |
| 流式输出 | 用户更早看到结果 | 不减少模型总计算量 |

应分别报告 TTFT、TPOT、吞吐、并发数、输入/输出长度分布和硬件，而不是只报“每秒 token”。

## 8. 故障与隔离

线上服务还需要：

- 请求长度和并发限制；
- 超时、取消和背压（Backpressure）；
- 健康检查与实例摘除；
- 敏感日志脱敏；
- 租户配额和权限；
- 模型版本、采样参数和错误轨迹记录。

一个超长请求若占满 KV Cache，会影响其他用户，因此容量控制也是隔离机制。
